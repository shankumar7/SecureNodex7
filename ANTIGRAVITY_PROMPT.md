# Antigravity Prompts for SecureNodeX

How to use: open the repo https://github.com/shankumar7/SecureNodex7 in Antigravity with `docs/` and `README.md` committed. Paste **Section 1 (Master prompt)** once at the start of a project/session. Then paste **one milestone prompt** (Section 2) per branch. Use Section 3 for reviews and fixes.

---
## 1. MASTER PROMPT (paste first)

You are a senior engineer building **SecureNodeX**, a decentralised, ECC-secured platform for IoT device identity, RBAC, digital-asset management, tamper-evident auditing and **split + replicated data storage**. This is a working prototype that must be demo-able and scalable.

**Source of truth.** Read these files completely, in order, before writing any code: `README.md`, `docs/00_PROJECT.md`, `docs/01_ARCHITECTURE.md`, `docs/02_SECURITY_PKI.md`, `docs/03_STORAGE.md`, `docs/04_CONTRACTS.md`, `docs/05_RBAC.md`, `docs/06_MESSAGE_FORMAT.md`, `docs/07_API_SPEC.md`, `docs/08_FIRMWARE_SPEC.md`, `docs/09_DEPLOYMENT.md`, `docs/10_TESTING_DEMO.md`, `docs/11_ROADMAP.md`, `docs/CONTRIBUTING.md`. These specs are binding. Requirement IDs (FR-*, NFR-*, AT-*) must be traceable in code comments/tests.

**Non-negotiable rules**
1. ECC only for asymmetric crypto: P-256 for devices/users/services/TLS/JWT(ES256)/ECIES; secp256k1 only for chain operator accounts. AES-256-GCM for data. Do not use RSA anywhere.
2. mTLS for device<->broker and all service<->service and node traffic. No plaintext internal HTTP, no `verify=False`, no disabled cert checks - not even in tests (use test CAs).
3. Never commit secrets. Keys/certs are generated by scripts into git-ignored paths. Provide `.env.example` only.
4. Deny by default. Every endpoint, topic and contract function has an explicit role check; every denial is audited.
5. Storage nodes only ever see ciphertext. Every uploaded object (from any source) is split into chunks and replicated R times on distinct nodes per docs/03. Verify hashes on every read.
6. Do not invent behaviour that contradicts the docs. If the spec is ambiguous or wrong: write the question to `docs/QUESTIONS.md`, choose the simplest compliant option, record an ADR in `docs/adr/`, and continue. Do not silently change message formats, manifest schema, contract interfaces or API paths.
7. Tests are mandatory: write tests with the code, run them, and show passing output. If you cannot run something (hardware), say so explicitly and provide a simulator or mock.
8. Do **not** write ESP32 firmware (humans do that). You may write the Python simulator and test vector tools that follow `docs/06` and `docs/08` exactly.
9. Small commits, conventional commit messages, one milestone per branch. Do not touch files outside the milestone scope except to fix bugs you introduce.
10. Prefer boring, readable code: Python 3.12 typed, FastAPI, SQLAlchemy 2 + Alembic, web3.py, `cryptography` library, aiomqtt, httpx, pytest; Solidity ^0.8.24 + OpenZeppelin v5 + Hardhat (TypeScript); Next.js 14 + TypeScript + Tailwind. Docker Compose, multi-arch images (amd64 + arm64) because Raspberry Pis run storage/gateway.

**Output format for each task**
(a) a short plan; (b) the implementation; (c) tests and their results; (d) how to run it (`make` targets); (e) a checklist mapping the milestone's acceptance tests (AT-*) to pass/fail; (f) open questions and risks. Be honest about anything unverified.

Confirm you have read the docs by listing, in 10 bullets, the architecture planes, the storage parameters (chunk size, R, W), the role list, the message signing input string, and the five contracts - then wait for my milestone prompt.

## 2. MILESTONE PROMPTS (paste one at a time)

### M0 - Repo skeleton
Implement Milestone M0 from `docs/11_ROADMAP.md`. Create the folder layout from README, root `.gitignore` (exactly per docs/09 section 10), `Makefile` with the targets in docs/09, GitHub Actions CI (lint + unit tests + gitleaks), `.env.example`, `deploy/docker-compose.dev.yml` with empty-but-healthy shells for api, worker, gateway, ca, storage (x3), postgres, broker placeholder. Each Python service exposes `/healthz` and `/metrics`. Add ruff/mypy/pytest config and a Next.js dashboard shell. Acceptance: `make dev-up` brings everything healthy; CI green.

### M1 - PKI and broker mTLS
Implement M1 per `docs/02_SECURITY_PKI.md` and `docs/06_MESSAGE_FORMAT.md`. Deliver: scripts to create offline root and online intermediate (P-256); `snx-ca` service (issue from CSR, certificate profiles for broker/device/service/storage-node, revoke, CRL generation, fingerprint calculation); `pki/provision-device.py` producing the device bundle (key, cert, chain, config.json) with correct file permissions; Mosquitto config with mTLS, identity-as-username, ECDSA-only ciphers; ACL/auth hook design (implement the HTTP auth plugin approach or the documented fallback and record an ADR). Add `tools/gen_test_vector.py` that outputs a keypair and a signed envelope following docs/06 section 3 (raw r||s) plus a verifier script. Tests: valid cert connects via `mosquitto_pub`/python client; unknown-CA cert, expired cert rejected (AT-06, AT-07); topic ACL test. Document exact commands.

### M2 - Smart contracts
Implement M2 per `docs/04_CONTRACTS.md` exactly: OperatorAccess, IdentityRegistry, StorageNodeRegistry, AssetRegistry (ERC-721 base with disabled standard transfers), DataRegistry (objects, grants, anchors), AuditLog (hash chain). Hardhat + TypeScript. Write a complete test suite: role matrix for every function, revoked-identity behaviour, terminal REVOKED, ERC-721 transfer disabling, anchor immutability, audit hash recomputation, operator-only access, fuzz test against privilege escalation. Provide `scripts/deploy.ts` (writes `deployments/<network>.json`, grants OPERATOR_ROLE, registers bootstrap admin) and ABI export script for the backend. Report gas usage. Do not change function signatures without an ADR.

### M3 - Backend core
Implement M3: FastAPI app `snx-api` per `docs/07_API_SPEC.md` (auth, principals, roles, devices, enrollment, audit, health), Postgres models + Alembic migrations, ES256 JWT with Argon2id passwords and rotating refresh tokens, RBAC dependency `require(permission)` matching `docs/05_RBAC.md` (deny by default), chain client (web3.py) wrapping all contract calls with retries and nonce management, event indexer worker that rebuilds DB state from chain events, audit service (writes `AuditLog.record` + DB copy), `/audit/verify` that recomputes the hash chain from chain events. Integrate with snx-ca for issuing certificates and registering identities on-chain. Tests: table-driven RBAC tests for every matrix cell, auth tests, indexer rebuild test, audit verify + tamper detection (AT-01, AT-17 API part, AT-19, AT-25 partial).

### M4 - Decentralised storage (most important)
Implement M4 exactly per `docs/03_STORAGE.md`. (1) `snx-storage` node service (mTLS-only; PUT/GET/HEAD/DELETE chunks, `/v1/replicate`, `/v1/inventory`, `/v1/health`; atomic fsync+rename writes; hash verification on PUT; sharded directories; streaming I/O). (2) Coordinator library used by the API: streaming chunking, AES-256-GCM per chunk with AAD, ECIES key wrapping for owner/grantees (docs/02 section 9), HRW placement, diversity rule, parallel writes with quorum W and fallback to next-ranked nodes, manifest + Merkle root, on-chain registration. (3) Read path with hash verification, replica fallback, Range support. (4) Worker: heartbeat monitor, node state machine, repair of under-replicated chunks with rate limiting, scrub, GC with grace. (5) Endpoints: objects CRUD/share/verify, `/objects/{id}/placement`, storage nodes + health. (6) Compose with 5 storage containers for local testing. Tests/chaos (must pass): AT-13, AT-14, AT-15 (kill node then download and match SHA-256), AT-16 (inspect disk: ciphertext only), AT-20 (corrupt chunk), AT-21 (kill 2 of 5), upload with a node killed mid-stream, fewer-than-W nodes returns 503 with no partial commit. Include a CLI `tools/snx_upload.py` and `tools/snx_download.py`. Print a placement table after upload for demo.

### M5 - Gateway, telemetry, anchoring
Implement M5 per `docs/06_MESSAGE_FORMAT.md`: `snx-gateway` subscribing over mTLS, full verification pipeline in the specified order (topic/cert match, device status cache <= 5 s with event-driven invalidation, timestamp window, replay via persisted last_seq, ECDSA verify using the on-chain-fingerprint-checked cert), per-device rate limiting, batching (100 msgs / 30 s), batch object through the M4 storage pipeline, Merkle tree + proof generation, `DataRegistry.anchorBatch`, `/batches` and proof endpoints, WebSocket stream, revocation propagation to broker (disconnect + deny within 5 s), audit events for every rejection type. Tests with the simulator and test vectors: AT-02, 03, 04, 05, 08, 09, 10, 11, 12.

### M6 - Simulator (not firmware)
Do NOT write ESP32 firmware. Build `simulator/` per `docs/10_TESTING_DEMO.md` section 5: batch-provision N device identities, run N asyncio virtual devices speaking the exact envelope/signing format over mTLS, with rate/jitter/offline windows and misbehaviour modes (tamper, replay, wrong topic, unknown CA, revoked). Output throughput/loss/latency percentiles. Also implement the cert-renewal flow client (`/enroll/renew`) so AT-22 can be tested without hardware.

### M7 - Dashboard
Implement `dashboard/` (Next.js 14, TypeScript, Tailwind) using a generated TS client from OpenAPI: login with role-based navigation; Devices (enroll, provision download once, status, revoke, rotate); Live telemetry (WebSocket) with signature/anchor badges and tx hashes; **Objects with upload from the browser and a Placement view** (chunks x nodes matrix with replica colours and node-down highlighting); Storage health (nodes, under-replicated count, repair activity); Assets (mint, transfer, history); Audit timeline with filters and "Verify chain" button; Principals/roles management. UI hides forbidden actions but never relies on that for security. Provide Playwright smoke tests for demo flows.

### M8 - Multi-host and Besu
Implement M8 per `docs/09_DEPLOYMENT.md`: Besu QBFT network (4 validators, genesis/key generation scripts, zero gas), per-host compose files (control, chain, storage, gateway) with multi-arch images, DNS/hosts guidance, remote storage nodes on Raspberry Pis, deployment of contracts to Besu, smoke test script `tools/smoke.sh` across hosts, and runbooks (`docs/runbooks/*.md`) for start/stop/replace-node/restore. Verify AT-23 (stop one validator).

### M9 - Hardening and demo
Implement chaos scripts in `tools/chaos/`, certificate rotation demo with short TTL, 500-device load test, index-rebuild tool (AT-25), metrics dashboards in Grafana, security review checklist against the STRIDE table in docs/02, and a one-command `make demo` that seeds users, devices, objects and assets. Run all AT-01..AT-25 and produce `docs/TEST_REPORT.md` with pass/fail and evidence. Fix defects. List any spec deviations with ADR links.

## 3. UTILITY PROMPTS

**Review prompt**
Review the current branch against the specs. For each requirement ID touched (FR-*, NFR-*), state whether it is satisfied, with file/line evidence and the test that proves it. List security issues (missing authz, unchecked certs, key handling, hash/signature verification gaps), spec deviations, and untested paths. Do not fix yet; output a prioritised list.

**Fix prompt**
Fix issue: <paste>. First write a failing test that reproduces it, then fix, then show all tests passing. Do not change public interfaces without an ADR.

**Spec-gap prompt**
Find contradictions, ambiguities and missing details across `docs/`. Output a table (file, section, problem, suggested resolution). Do not edit the docs; I will decide.

**Explain prompt (for viva/judges)**
Explain this module for a judge in plain language: what it does, which requirement it satisfies, one diagram in ASCII, and the 3 hardest questions a judge might ask with answers.
